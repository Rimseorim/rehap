# 페르소나 8: 41세 여 · 수평 프레스

## 프로필
- IT숙련도: 미숙 / 증상설명정확도: 부정확 / 증상민감도: 예민 / 병원권유수용도: 거부감 / 크로스핏경력: 숙련
- 시나리오: 흉근(가슴) 통증, 애매한 증상설명이 오분류로 이어지는지 검증
- 참고: 통증부위 확인 결과 "수평 프레스"는 앱에서 **흉근** 부위에서만 선택 가능했다(어깨 선택 시 목록에는 뜨지 않음, 별도 확인 완료). 당초 가정("가슴 또는 어깨")과 달리 흉근 단일 경로였음을 명시.

## 진행 기록
1. 로그인: "데모로 시작" 링크 클릭 → 정상 진입. IT미숙 페르소나 기준으로도 "데모로 시작" 링크가 작고 하단에 위치해 찾는 데 시간이 걸릴 만한 위치였음(문제로 별도 기록).
2. 기록 탭이 기본 화면 → 재활 탭으로 이동. 하단 탭바 아이콘만으로 "재활"을 인지해야 해서 IT미숙 사용자는 아이콘 문구를 한 번 더 확인하는 모습이 예상됨.
3. 재활 홈 "지금 시작하기" 클릭 → **버그**: 이전 세션(다른 통증부위)의 저장된 진행 상태(localStorage)가 남아있어 즉시 엉뚱한 화면(예: 다른 부위의 동작 선택/원인 확정 화면)으로 튐. 새로고침 없이 홈 아이콘(⌂)으로 되돌아가야 정상적인 "통증 부위" 선택 화면(10%)이 나타남. IT미숙 사용자라면 "왜 내가 선택한 적 없는 화면이 뜨지?"라고 당황할 가능성이 큼.
4. 통증 부위 선택 화면(8개 부위: 무릎/허리/발목/어깨/고관절/손목/팔꿈치/흉근) → "흉근" 클릭.
5. 동작 선택 화면(흉근) → 옵션이 "수평 프레스" 단 1개만 존재. 클릭.
6. 감별질문 1 "통증이 언제 느껴지나요?" (바를 내릴 때 / 밀어 올릴 때 또는 내내 / 쉬는 중에도 욱신거린다) → 페르소나 특성(부정확+예민, 위치/양상은 애매하게)에 따라 **가장 포괄적인 선택지 "밀어 올릴 때 또는 내내"** 선택.
7. 감별질문 2 "어떤 느낌인가요?" (전체적으로 뻐근하고 무거워요 / 가슴 근육이 당기거나 뻐근해요 / '뚝' 소리·찢어지는 느낌) → 마찬가지로 가장 애매하고 비특이적인 **"특별히 당기는 느낌 없이 전체적으로 뻐근하고 무거워요"** 선택.
8. 원인 확정 화면(82%) → "과사용 (볼륨·빈도 급증)"으로 판정. 화면 하단에 빨간 경고 박스로 "관절이 눈에 띄게 부어있어요 / 만지면 열감이 느껴져요 / 미는 순간 '뚝' 소리와 함께 가슴이 심하게 멍들었어요" 위험 신호 안내와 "재활 전 전문의 진단을 먼저 받으세요" 문구 노출. 페르소나는 병원권유수용도=거부감이므로 이 경고를 읽고도 그대로 "재활 루트 보기" 클릭(의도된 행동, 앱이 이를 막지 않는 것은 설계상 정상 — 위험신호는 "감지 시 자동 전환"이 아니라 정보 제공형이라 사용자가 무시할 수 있는 구조임에 유의).
9. "재활 루트 보기" 클릭 → **심각한 데이터 버그 발견**(아래 상세).
10. 이후 "기록" 탭 확인 결과 오늘 기록 목록에는 "수평 프레스 / 흉근 · 과사용 (볼륨·빈도 급증)" 카드가 정상적으로 남아 있어, 감별 자체는 완료·저장됨을 확인.
11. 그러나 "재활" 홈 화면의 "재활 진행 중" 카드는 여전히 이 세션과 무관한 기존 번들 데모 데이터("스쿼트 · 무릎")만 표시 — 새로 진단된 흉근 루트로 갱신되지 않음(아래 상세).

## 발견된 문제

- **[정정]** 원래 "운동 콘텐츠 교차오염(데이터 버그, 최상위 심각도)"으로 보고했으나 검토 결과 오판정으로 확인됨. index.html의 BUNDLED 데이터를 직접 파싱해 `press-horizontal > chest > cause-c > stage-1.phase_a`를 확인한 결과, 보고서가 지목한 4개 운동(어깨 후방 관절낭 스트레칭, 전완 회내·회외 스트레칭, 하부 승모근 Y-raise, 밴드 어깨 외회전 강화)은 실제로 cause-c(흉근·과사용) 데이터에 `set:"a_b"` 항목으로 정상 등록되어 있고, 각 운동의 `why` 필드에도 "소흉근 단축으로 인한 견갑 전방 경사 보완", "벤치프레스 패턴 개선" 등 흉근/수평 프레스 재활과의 명시적 연관성이 기술되어 있음. 즉 벤치프레스 재활 프로토콜의 정상적인 견갑/회전근개 보조운동이며 버그가 아님. 또한 코드 구조상(`route()` 함수 등) 이 경로는 in-memory 상태(S.movementId/painSiteId/causeId)만으로 BUNDLED 정적 데이터를 조회하며 localStorage를 거치지 않으므로, 동시 탭 실행(페르소나7 세션과의 교란)으로 인한 교차오염 가설도 성립하지 않음. 다만 화면상 "왜 이 운동인가" 설명 문구가 흉근 통증과 바로 연결되지 않아 순간적으로 "왜 어깨/전완 운동이 나오지?"라는 의문이 들 수는 있었음 — 큰 사용성 문제는 아니며, 필요 시 설명 문구를 "벤치프레스 패턴/견갑 안정성 보완"임을 더 명확히 드러내는 정도로 개선하면 충분함. — 위치: 재활 루트 화면(`route()`, "기초 재활" 단계 "오늘의 준비운동" 섹션)
- **[심각도: 사용성]** "지금 시작하기" 버튼이 항상 새 진단 흐름(통증 부위 선택)으로 가지 않고, localStorage에 남은 이전 미완료/완료 세션 상태로 즉시 점프하는 경우가 있었음. 새로 감별을 시작하려는 사용자가 의도치 않게 과거 화면(예: 이미 완료한 다른 부위의 원인 확정 화면)을 보게 되며, 이때 되돌아가는 방법이 직관적이지 않음(홈 아이콘 클릭 필요, 별도 "새로 시작" 버튼 없음). IT미숙 페르소나 기준으로 혼란 가능성 높음. — 위치: 재활 홈 화면 "지금 시작하기" 버튼
- **[심각도: 사용성/데이터]** 새 진단을 완료(원인 확정 → 재활 루트 보기)해도 재활 홈 화면의 "재활 진행 중" 카드가 갱신되지 않고 기존 무관한 카드("스쿼트 · 무릎")를 계속 보여줌. 확인 결과 이는 백엔드 기록 저장 API(`/records/save`) 호출 실패 시(`LAST_RECORD` 갱신 실패) 화면 하단에 작은 "기록 저장에 실패했습니다." 토스트만 뜨고 넘어가는 구조 때문으로 보임 — 로컬 테스트 환경에 백엔드 서버가 없어 발생한 것일 가능성이 높으나(운영 환경(Railway)에서는 재현되지 않을 수 있음), 만약 운영 환경에서도 네트워크 문제로 저장에 실패하면 사용자는 전체 감별 질문에 답한 뒤에도 홈 화면에서 아무 진전도 확인할 수 없고, 작은 토스트 문구 외에는 실패를 알아차릴 단서가 없음. 재시도 버튼이나 로컬 폴백(예: 방금 확정된 cause를 기준으로 홈 카드 임시 표시) 없이 조용히 실패함. — 위치: `saveRehabRecord()` 및 재활 홈 화면 "재활 진행 중" 카드
- **[심각도: 사용성]** "데모로 시작" 링크가 화면 하단에 작은 텍스트로만 존재해 IT미숙 사용자 기준 인지에 시간이 걸릴 위치(재확인 필요한 수준은 아니나 다른 카카오/네이버/구글 로그인 버튼 대비 시각적 위계가 매우 낮음).

## 최종 결과
- 배정된 cause/루트: 흉근 · 수평 프레스 → **과사용 (볼륨·빈도 급증)** (cause-c). 원인 확정까지는 데이터/로그(기록 탭)상 정상적으로 완료·저장됨.
- 시나리오 의도와 일치 여부: **부분 일치**. "애매한(포괄적) 답변이 잘못된 cause로 이어지는가"라는 관점에서는, 흉근/수평프레스 분기가 단 2개 질문으로 즉시 cause-c(과사용)로 수렴하는 얕은 구조라 애매한 답변이 오분류를 유발했다고 단정하기는 어려움 — 다만 두 질문 모두에서 "가장 넓고 특이성 없는" 선택지를 고르면 곧바로 과사용으로 판정되는 구조 자체가, 실제로는 구조적 원인(소흉근 단축 등, cause-b/d 경로)일 수 있는 사용자를 "증상을 구체적으로 설명하지 못한다"는 이유만으로 과사용으로 오분류할 위험을 내포함(이는 오분류라기보다 "분기 얕음"에 가까움, 기존에 기록된 "감별 분기 얕음 패턴"과 같은 계열 이슈로 판단됨). 당초 "운동 콘텐츠 교차오염" 데이터 버그로 의심했던 부분은 검토 결과 오판정으로 확인됨(위 "발견된 문제" 참조) — 해당 운동들은 cause-c에 정상 등록된 견갑/회전근개 보조운동이며 원칙 2 위반 사례가 아님. 다만 localStorage 단일 키로 인한 이전 세션 점프와 `/records/save` 실패 시 무피드백 문제는 실재하며 조치가 필요함.
